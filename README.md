# Сравнение пакетов ALT

Статический сайт на Svelte 5, TypeScript и Vite. Сохранён исходный режим «Сравнение веток». Режим «Компоненты и пакеты» показывает явные пакеты компонентов «Альт Сервер» и «Альт Домен» по определениям актуального пакета `alt-components-base` в p11, их версии в ISO 11.1, текущем p11 и Sisyphus. База выпуска 11.1 подготовлена один раз и включена в сайт; актуальные p11 и Sisyphus получаются через API, сравнение вычисляется браузером. В интерфейсе нет привязки к руководствам, редакторских решений и анализа зависимостей.

## Запуск

```sh
npm ci
npm run dev
```

Откройте адрес, который выведет Vite (обычно `http://localhost:5173/`), и выберите «Компоненты и пакеты». Для проверки:

```sh
npm run check
npm test
npm run build
```

Для проверки соответствий в Chromium запустите Vite и в другом терминале выполните `node tests/browser-provides.mjs`. Скрипт проверяет обе редакции и архитектуры, широкий и узкий экран, фильтры и панель пакета. `node tests/browser-changelog.mjs` дополнительно проверяет быстрое переключение веток, отсутствие пакета, ошибку источника, смену RPM только в Sisyphus и отсутствие базовой версии. Неоднозначность и changelog проверяются на перехваченных тестовых ответах только внутри браузера. При необходимости задайте `TEST_BASE_URL` и `CHROMIUM_PATH`.

Изменения не публикуются автоматически при локальном запуске. В репозитории имеется GitHub Actions workflow публикации при push в `main`; без отдельного указания его не запускайте.

## Получение данных в браузере

Запуск генератора перед открытием страницы **не нужен**. `src/doc/runtime.ts` загружает `public/releases/11.1/manifest.json` и фиксированный снимок выбранной архитектуры с того же сайта, проверяет SHA-256 и исторические идентификаторы. Для p11/Sisyphus выполняются прямые запросы к исходным API; `model.ts` вычисляет различия. Файлы `public/doc-data/p11-*.json` и `sisyphus-*.json` остаются только материалами подготовки/тестов и не используются вместо актуальных веток. Исходный режим сравнения веток по-прежнему хранит пользовательские группы и настройки в localStorage.

При каждом открытии режима или смене архитектуры:

1. С сайта загружаются манифест выпуска и статический JSON с пакетами образа, UUID, историческими определениями, подтверждёнными epoch и соответствиями Provides. API образов и исторический Git-тег в браузере не запрашиваются.
2. Параллельно загружаются полные экспорты p11 и Sisyphus для выбранной архитектуры и `noarch`. У ответов проверяются ветка, архитектура, длина и поля RPM.
3. Версия активного `alt-components-base` в p11 задаёт текущий тег. Его исходная сборка проверяется по точной ветке и version-release через `/site/source_package_versions`. Исторический тег уже включён в базу 11.1 и соответствует `alt-editions-server` из образа.
4. Через API Forgejo `https://altlinux.space/api/v1/repos/alterator/alt-components-base/tags/<tag>` подтверждается текущий тег и его коммит. ZIP-архив запрашивается по этому коммиту; `fflate` распаковывает определения, `smol-toml` разбирает реальные `.edition`, `.component`, `.category`. Произвольный master не используется. Обрабатываются все разделы обеих редакций, включая опциональные.
5. Для отсутствующих буквальных имён проверяются RPM-поставщики отдельно в p11 и Sisyphus. Исторические поставщики и полные версии берутся только из фиксированной базы, не меняются вслед за ветками и не проверяются заново при открытии пакета.

Сначала появляется базовая таблица после получения фиксированного снимка 11.1, p11 и текущих определений. Проверки Provides актуальных веток и загрузка Sisyphus продолжаются ограниченной очередью; пока они не закончены, строка помечена «проверяется». Открытие компонента или пакета повышает приоритет запросов.

На экране остаются состояние загрузки, ошибки и состояния строк пакетов. Кнопки обновления/очистки кеша, даты и идентификаторы получения снимков, технические счётчики и сообщения о кеше убраны. Для повторного получения актуальных данных перезагрузите страницу или заново откройте режим. Внутренние метрики загрузчика сохранены для диагностики; дополнительные запросы выполняются с ограниченной параллельностью, при HTTP 429 предусмотрены повторы.

В IndexedDB браузера кешируются архив актуальных определений по коммиту, RPM Provides по хешу и последний полностью успешный результат. Каталог p11/Sisyphus запрашивается заново. При необходимости кеш удаляется через средства браузера (база IndexedDB `alt-components-runtime-v1`); база 11.1 в файлах сайта и настройки сравнения веток сохраняются. Если IndexedDB недоступен, используется память вкладки. Неудачное обновление не заменяет последний полный результат: он восстанавливается из кеша с сообщением об ошибке. При смене архитектуры старые данные другой архитектуры не показываются, устаревшие запросы отменяются. Отсутствие или неверная контрольная сумма статической базы дают явную ошибку; автоматического получения новой базы из p11 нет.

Теперь работоспособность зависит от доступности **обоих** API и их политики CORS. Forgejo API разрешает CORS для обычного браузера, но защита `altlinux.space` может вернуть страницу Anubis вместо API, в частности стандартному headless-браузеру. Приложение не обходит защиту и не подменяет ответ локальными данными. Онлайн-проверки должны выполняться с обычным браузерным профилем; синтетические браузерные проверки перехватывают исходные сетевые запросы через `tests/runtime-fixtures.mjs` и ускоряют только тестовые таймеры. Тестовые перехваты отсутствуют в коде приложения.

Для регрессии автоматической загрузки, повторного открытия режима, отказа источника и узкого экрана: `node tests/browser-runtime.mjs`. Для проверки реальных запросов без фикстур и ускорения времени: `LIVE_RUNTIME=1 node tests/browser-runtime.mjs`.

## Подготовка фиксированного выпуска

Снимки 11.1 уже находятся в `public/releases/11.1/`. Для них подтверждены исходный состав (3116 RPM x86_64, 3051 RPM aarch64), исторический тег/коммит и известные Provides. При подготовке дополнительно подтверждены полные EVR всех наблюдаемых RPM образа (635 и 618 соответственно), включая epoch=0, по точным хешам.

Для первоначальной подготовки другого выпуска сначала получите промежуточные нормализованные снимки, затем зафиксируйте их:

```sh
python3 scripts/update-doc-data.py --release 11.1
npm run prepare:release -- --release 11.1
```

Нужны Node.js 22.6+, Python 3.11+, Git и сетевые источники. Для существующего клона `alt-components-base` можно указать `--repo /path/to/alt-components-base`. Генератор сохраняет промежуточные JSON в `public/doc-data/`. `prepare-release.mjs` принимает `--input-dir` с `image-<release>-<arch>.json` и `p11-<arch>.json`, подтверждает UUID, полный состав/хеши образа, исторический Git-коммит и Provides, дополняет epoch наблюдаемых RPM. Схема снимков описана типом `Snapshot` в `src/doc/model.ts`; неполные данные и ошибки источников прерывают подготовку до публикации. `--skip-epoch-checks` разрешает явно неполный импорт: неизвестные epoch остаются неизвестными.

Скрипт создаёт отдельный каталог `public/releases/<release>/` целиком через атомарное переименование. Файлы названы по архитектуре и SHA-256; манифест хранит UUID, количество RPM, тег/коммит и дату фиксации. Повторный запуск проверяет существующие файлы и **не перезаписывает выпуск**, независимо от изменений промежуточных данных. Обычное обновление p11, очистка кеша и сборка сайта этих файлов не меняют. Новый выпуск готовится в новом каталоге; его выбор в интерфейсе пока требует отдельного добавления. Статические файлы включаются в сборку Vite автоматически и публикуются вместе с сайтом только при разрешённой публикации.

Версия текущего каталога выбирается автоматически по `alt-components-base` из актуального бинарного экспорта p11. Его исходный пакет подтверждается через ALTRepo `/site/source_package_versions`, с точным совпадением ветки и version-release. История этого API может содержать несколько сборок: выбирается сборка активного пакета в экспорте. Версия `alt-editions-server` проверяется на соответствие тому же исходному пакету; `edition_domain` читается из определений этого тега и не требует отсутствующего в p11 отдельного RPM `alt-editions-domain`. Затем читается только соответствующий Git-тег. Фиксации `0.10.8-alt1` и параметра `--definition-tag` больше нет. Если новая версия появится в p11, новое получение данных автоматически обновит каталог — теперь и в браузере, без запуска скрипта.

В `definitions.package` сохраняются полная RPM-версия, ветка p11, хеш исходного RPM и источник подтверждения; в `definitions.tag` и `revision` — выбранный Git-тег и коммит. Несовпадение данных API/архитектур/редакций или отсутствие тега прерывает обновление до записи рабочих JSON и сохраняет последние успешные данные.

Источники:

- [alt-components-base](https://altlinux.space/alterator/alt-components-base), тег активного пакета p11 для текущего каталога и тег `0.10.3-alt1` для состава 11.1; последний сверяется с официальными [списками файлов ISO x86_64](https://download.basealt.ru/pub/distributions/ALTLinux/p11/images/server/x86_64/alt-server-11.1-x86_64.iso.txt) и [aarch64](https://download.basealt.ru/pub/distributions/ALTLinux/p11/images/server/aarch64/alt-server-11.1-aarch64.iso.txt);
- [пакеты образа «Альт Сервер» 11.1](https://packages.altlinux.org/ru/p11/images/alt-server/p11:alt-server:::release.11.1.0:x86_64:install:iso/packages/) через API ALTRepo `/image/image_uuid_by_tag` и `/image/image_packages`;
- экспорты бинарных пакетов [p11](https://rdb.altlinux.org/api/export/branch_binary_packages/p11) и [Sisyphus](https://rdb.altlinux.org/api/export/branch_binary_packages/sisyphus) для выбранной архитектуры и `noarch`.

У каждого снимка есть идентификатор, источник, время получения и архитектура. Версии сравниваются по правилам RPM для epoch/version/release, а не как строки. Изменение состава компонентов определяется по определениям двух тегов; обновление версий определяется отдельно, даже если определения не изменились. По нажатию на пакет открывается панель с версиями, затронутыми компонентами и changelog. Ячейки версий p11 и Sisyphus работают как кнопки: выбирают диапазон «образ 11.1 → выбранная ветка», её исходный пакет и ссылку на полный источник. При открытии нового пакета выбрана p11. Старый запрос отменяется при переключении или закрытии панели.

Changelog загружается для исходного пакета реального RPM выбранной ветки. Хеш сборки определяется по точной ветке и version-release из снимка; произвольная первая строка истории или другой ветки не используется. Если версия из образа неизвестна или реальный RPM изменился, показываются доступные записи выбранного RPM с явным пояснением, что диапазон от 11.1 не определён. Недоступность источника, отсутствие пакета и неоднозначность поставщиков обозначаются для конкретной ветки. Браузерный доступ к changelog требует соединения с ALTRepo API.

Рядом с фильтрами раздела и категории находится один компактный список: «Все пакеты», «Обновлены», «Включены в компонент», «Исключены из компонента», «Сменился RPM-поставщик», «Без изменений». Фильтр работает совместно с поиском; в таблице остаются только подходящие пакеты. «Без изменений» отбирает неизменившиеся пакеты, даже если другие пакеты этого компонента обновились. «Все пакеты» возвращает полный состав, включая строки с отсутствующими или неполными данными. Дополнительных фильтров компонентов и состояния данных в интерфейсе нет.

## Сопоставление через Provides

Имя в `[packages]` компонента не всегда является именем отдельного бинарного RPM. Например, `gvfs-utils` предоставляет `libgio`, `kea-shell` — `kea-admin`, а `cups-ppd` — `cups`. Загрузчик сначала ищет точное имя, затем для отсутствующих имён получает кандидатов через ALTRepo `/dependencies/packages_by_dependency` с `dp_type=provide`. Кандидаты проверяются по полному экспорту той же ветки и архитектуры, их `Provides` подтверждается по точному хешу RPM. Поиск и версии p11 и Sisyphus не смешиваются.

В JSON `packages` остаётся каталогом реальных RPM. Поле `providers` хранит отдельные связи от имени в компоненте к реальным RPM, ссылки на доказательства и признак полноты поиска. В таблице сохраняется исходное имя компонента, а под версией показывается `RPM: <имя> · Provides`. В панели доступны ссылки на метаданные. Сравнивается полный EVR **реального RPM**, а не версия виртуального `Provides` (они могут различаться). Несколько подходящих RPM — явная неоднозначность, без автоматического выбора версии. Смена реального поставщика отмечается отдельно; единый диапазон changelog разных RPM автоматически не строится. Поиск учитывает и имена поставщиков.

Для образа 11.1 кандидат при подготовке проверяется по хешу **RPM из этого образа**, не по его нынешней версии в p11. UUID, исторические определения и соответствия фиксируются в файлах выпуска. Поиск исторических поставщиков пока целевой: кандидаты берутся из веток и ранее подтверждённых соответствий, полного обхода `Provides` всех RPM образа нет. Если целевой поиск не подтвердил поставщика, это `complete=false` / «RPM-поставщик не определён». `providerCheckedNames` хранит имена, учтённые при подготовке. Для нового имени из будущих определений p11, отсутствующего в исторических RPM и списке проверки, показывается неизвестный поставщик вместо ложного удаления. Наличие общего исходного пакета само по себе не создаёт соответствия — расширения `gtkhash-*` не подставляются вместо `gtkhash`.

`scripts/provides.py` отделяет получение соответствий от сравнения и интерфейса. Файл `rpm-provides-cache.json` кеширует только `Provides`/`Obsoletes` и источник по неизменяемому хешу RPM, без списка `Requires`; зависимости в интерфейс не возвращаются. Ошибка API, неполный ответ или несовпадение с экспортом прерывают подготовку данных до записи рабочих снимков. Проверки получения данных используют Python и синтетические офлайн-фикстуры в `tests/provides_reader_test.py`; они запускаются вместе с `npm test`.

## Важные ограничения данных

ISO «Альт Сервер» используется как источник версий 11.1 для **обеих** редакций. Отдельный образ с тегом `alt-domain` для 11.1 не найден. Если пакета нет в этом ISO, приложение пишет «нет в образе» и **не** утверждает, что пакета не было в выпуске или в репозитории; опциональные компоненты могут в ISO не входить.

API списка образа отдаёт version-release, но не epoch и не имя исходного пакета. Префикс `1:` в версиях p11/Sisyphus — реальный RPM epoch. При подготовке фиксированного выпуска changelog запрашивается **по хешу бинарного RPM из ISO**: верхняя запись и хеш ответа должны точно соответствовать RPM образа. Полный EVR и `epochSource` записываются в статический снимок. В браузере версия 11.1 больше не изменяется при выборе пакета. У неполного импортированного снимка неизвестный epoch остаётся явным ограничением сравнения и changelog. Исторические имена исходных пакетов могут быть выведены из p11 во время подготовки и не являются подтверждением исторического соответствия. Тип изменения и фильтры относятся к 11.1 → p11; Sisyphus доступен отдельной колонкой и через переключение changelog.

Определения 11.1 и текущий каталог p11 берутся из разных тегов. В таблице перечислены явно заданные обычные пакеты компонентов с учётом `arch` и `exclude_arch`. Записи с `kernel_module = true` показаны отдельно как шаблоны модулей ядра: имя без суффикса ядра не классифицируется как удалённый RPM. Выбор конкретного варианта ядра пока не реализован. Отсутствие пакета в p11, исключение из компонента и отсутствие в ISO — разные состояния. Сайт статический, серверного прокси нет. При неудаче обновления сохраняется последний успешный результат в браузере; фиксированная база 11.1 остаётся в файлах сайта.
